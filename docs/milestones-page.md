# The Babel Milestones page

Generated by [`milestones_page.py`](../src/babel_validation/tools/milestones_page.py).
**Not currently published**: see "Publishing" below, which has to be rebuilt on top of the
dashboard site before this page appears anywhere.

## The problem

Babel work is spread over five repositories in two organizations (Babel, NodeNormalization,
NameResolution, babel-validation, babel-explorer). Milestones are the commitment mechanism —
when something needs dealing with by a soft deadline, it goes in a milestone — but milestones
cannot span repositories, so "what have I committed to?" means visiting five separate pages.

## Why a generated page rather than a project board

A GitHub Project spanning the repositories was the obvious alternative, and was rejected:

- **A board is a second record of commitment.** It has to be kept in step with the milestones
  by hand, and it drifts the moment that stops happening. This page is *derived* — the
  milestone is the only input, so there is nothing to keep in sync.
- **Boards can't answer the outside question.** The most useful thing here is telling someone
  who filed an issue roughly when it'll be looked at. A public URL does that; a board does not.
- **Automating a board is expensive.** The built-in auto-add workflow filter supports only
  `is`/`label`/`reason`/`assignee`/`no` — not `milestone:` — and never removes items, so
  keeping a board in step with milestones needs an Action in all five repositories listening
  for `milestoned`/`demilestoned`, plus a PAT with `project` scope stored as an organization
  secret in both organizations.

What is given up: manual rank-ordering within a milestone. A `priority:` label is the
intended substitute, since labels are readable with the same token as everything else.

## Constraint worth preserving

Every repository listed is public, so a workflow's built-in `GITHUB_TOKEN` can read all of
them across both organizations — no secrets to configure or rotate. Reading anything off a
GitHub Project would break this, because `project` scope requires a PAT. Keep priority and
component in labels.

## Publishing

**This has to be rebuilt, and it is deliberately not written yet.** The first version of this
page came with three pieces of wiring — a `milestones-page.yaml` workflow deploying to
`gh-pages:milestones/`, a `clean-exclude: milestones/` added to
`deploy-website-to-gh-pages.yaml`, and a link from `website/src/pages/index.astro` — and the
dashboard PR (#120) invalidates all three: it deletes `deploy-website-to-gh-pages.yaml`
outright, replaces `index.astro`, and publishes the whole site from `dashboard.yaml`. Rather
than leave wiring that merges cleanly and then silently does the wrong thing, all three were
removed; the tool, its tests and this document are what remain. They are recoverable from this
branch's history if a detail is needed.

What a rebuilt version has to account for:

- **Only one workflow should write `gh-pages`.** `dashboard.yaml` deploys `website/dist` to the
  root of the branch with `JamesIves/github-pages-deploy-action`, which cleans by default —
  so a separate workflow publishing `milestones/` gets its output deleted by the next daily
  dashboard run, and nothing serialises the two: they would need the same `concurrency` group,
  and the dashboard deploy would need `clean-exclude: milestones/`.
- **Folding the generation into `dashboard.yaml` avoids that entirely**, and is the preferred
  direction: it already runs daily, already builds and deploys the site, and one deploy that
  writes everything cannot race a second one. `milestones_page.py` writes a self-contained
  HTML file, so it can simply write into `website/dist/milestones/` (or `website/public/`)
  before the build, with no second deploy step and no `clean-exclude` at all.
- **The link belongs in the new navigation**, `website/src/components/NavBar.astro`, not in
  the index page that #120 replaced.
- **Cadence.** The old workflow ran at 06:17 UTC, ahead of the dashboard's 06:30. Folded in, it
  runs when the dashboard runs, which also means it is only as fresh as the test suite that
  gates it — acceptable for milestones, but worth stating.

## Not done yet

- Priority/component labels aren't surfaced or sorted on — all labels render undifferentiated.
- Closed milestones are ignored, which hides ~253 open Babel issues parked in closed
  milestones (`Needed soon`, `Needs tests`, `Needs investigation`, …).
- No grouping by repository or component; one flat chronological list.
- The legacy priority-bucket milestones are recognised by title in `BUCKET_TITLES`. If they
  get cleaned up, drop that list.
