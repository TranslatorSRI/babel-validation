# The Babel Milestones page

Generated by [`generate_milestones.py`](../src/babel_validation/tools/generate_milestones.py).
Published at
[/babel-validation/milestones/](https://translatorsri.github.io/babel-validation/milestones/),
as a page of the dashboard site.

## The problem

Babel work is spread over five repositories in two organizations (Babel, NodeNormalization,
NameResolution, babel-validation, babel-explorer). Milestones are the commitment mechanism —
when something needs dealing with by a soft deadline, it goes in a milestone — but milestones
cannot span repositories, so "what have I committed to?" means visiting five separate pages.

## Why a generated page rather than a project board

A GitHub Project spanning the repositories was the obvious alternative, and was rejected:

- **A board is a second record of commitment.** It has to be kept in step with the milestones
  by hand, and it drifts the moment that stops happening. This page is *derived* — the
  milestone is the only input, so there is nothing to keep in sync.
- **Boards can't answer the outside question.** The most useful thing here is telling someone
  who filed an issue roughly when it'll be looked at. A public URL does that; a board does not.
- **Automating a board is expensive.** The built-in auto-add workflow filter supports only
  `is`/`label`/`reason`/`assignee`/`no` — not `milestone:` — and never removes items, so
  keeping a board in step with milestones needs an Action in all five repositories listening
  for `milestoned`/`demilestoned`, plus a PAT with `project` scope stored as an organization
  secret in both organizations.

What is given up: manual rank-ordering within a milestone. A `priority:` label is the
intended substitute, since labels are readable with the same token as everything else.

## Constraint worth preserving

Every repository listed is public, so a workflow's built-in `GITHUB_TOKEN` can read all of
them across both organizations — no secrets to configure or rotate. Reading anything off a
GitHub Project would break this, because `project` scope requires a PAT. Keep priority and
component in labels.

## Publishing

A page of the dashboard site, not a thing published next to it. `dashboard.yaml` runs the
generator in its own `milestones` job, which writes `data/milestones.json`; `publish` builds
the Astro site and makes the single write to `gh-pages`.

The first version did it the other way — its own `milestones-page.yaml` deploying to
`gh-pages:milestones/`, a `clean-exclude: milestones/` on the site's deploy, and a link from
the old `index.astro` — and that is worth recording, because it was one merge away from
breaking silently. `JamesIves/github-pages-deploy-action` cleans by default, so the dashboard's
daily deploy would have deleted `milestones/` on its first run after both landed. Keeping two
publishers alive means a shared `concurrency` group *and* a `clean-exclude`, two things that
have to stay in step forever and fail quietly when they don't. One publisher has neither.

What that decision bought, beyond not breaking:

- **The page is in the site.** Nav bar, theme, dark mode, and the same untrusted-text rules as
  the rest of the report — the tool emits JSON and a Vue island renders it, rather than the
  tool emitting a standalone HTML document with its own inline CSS.
- **The repository list is `targets.ini`'s `Repositories`**, not a second copy. That list is
  already exactly this family of repositories, and the workflow's target loop has already
  drifted from `read_targets()` once. If "whose assertions do we run" ever stops meaning
  "whose milestones do we track", add a `MilestoneRepositories` key that falls back to it.
- **A failure here cannot take the dashboard down, or vice versa.** The two jobs are
  independent, and `publish` refetches the last published copy of any file this run did not
  produce — the deploy cleans the branch, so a missing file would otherwise be a deleted page.
  The page stamps the date it was generated, so a carried-forward copy reads as stale.

**Cadence.** The old workflow ran at 06:17 UTC, ahead of the dashboard's 06:30. It now runs
when the dashboard runs. It does *not* wait for the test suite — that was the reason for a
separate job rather than another step — so it is as fresh as the run, not as fresh as the
slowest environment in it.

## Not done yet

- Priority/component labels aren't surfaced or sorted on — all labels render undifferentiated.
- Closed milestones are ignored, which hides ~253 open Babel issues parked in closed
  milestones (`Needed soon`, `Needs tests`, `Needs investigation`, …).
- No grouping by repository or component; one flat chronological list.
- The legacy priority-bucket milestones are recognised by title in `BUCKET_TITLES`. If they
  get cleaned up, drop that list.
